# Roomly 1.4: телефон +996 и пароль

Обновление удаляет клиентский вход через Google. Email и пароль остаются резервным способом входа. Рабочая база и облачные настройки при подготовке обновления не изменялись.

## Порядок внедрения

1. Сохраните резервную копию существующей базы и файлов сайта. Проверьте восстановление копии в тестовой среде.
2. На копии базы выполните `supabase/006_phone_preflight.sql`. Это только чтение. Сохраните количество пользователей, бронирований, записей журнала и распределение ролей/доступа. Если обнаружены дубли email либо сторонние внешние ключи к `members`, остановитесь и разберите зависимости; не применяйте CASCADE.
3. На той же копии выполните `supabase/006_phone_identity.sql`. Миграция рассчитана на существующую схему Roomly после 001/004/005. Она выполняется в транзакции, не удаляет аккаунты, роли, блокировки, брони или журнал. Старые миграции 003/004/005 ПОСЛЕ неё повторно не запускайте: они содержат прежние функции доступа по email.
4. Сравните исходные количества и проверьте Email-вход текущего администратора, запрет для отключённого сотрудника, просмотр старых броней, регистрацию телефона, SMS и сохранение новой брони. Сценарии автоматической проверки описаны ниже.
5. Только после успешной проверки примените 006 к рабочей базе в согласованное время: миграция кратковременно блокирует запись в таблицы аккаунтов и доступа. При SQL-ошибке транзакция откатывается; исправьте причину на копии. Не удаляйте таблицы для повторного запуска.
6. Загрузите содержимое архива обновления в корень существующего GitHub-репозитория с заменой файлов. Настроенный `config.js` не заменяйте — он не включён в архив. Скрипт и CSS уже имеют новую версию кеша. Применить миграцию необходимо ДО публикации нового интерфейса.

## Supabase Phone Provider и SMS

В существующем проекте откройте Authentication → Sign In / Providers → Phone (названия разделов могут различаться). Включите Phone и подтверждение телефона. Сохраните Email Provider и его SMTP на период перехода. Пароль: минимум 12 символов. OTP: 6 цифр; задайте срок действия, например 5 минут, и интервал повторной отправки не меньше 60 секунд.

Выберите поддерживаемого SMS-провайдера, например Twilio, MessageBird или Vonage. До подключения убедитесь в доставке на мобильные номера Кыргызстана +996 и ограничениях отправителя у самого провайдера.

Для Twilio: создайте/используйте SMS Messaging Service и отправителя, разрешите доставку в Кыргызстан; в Supabase укажите Account SID, Auth Token и Messaging Service SID в соответствующих полях провайдера. У тестового аккаунта провайдера могут быть ограничения адресатов. Проведите доставку на реальный номер и проверьте журнал доставки. Параметры SMS-провайдера и его секреты хранятся ТОЛЬКО в Supabase, не в GitHub или config.js.

Реализация работает с `/signup` (phone + password), `/token?grant_type=password`, `/verify` (type=sms), `/resend` (type=sms). При отключённом Confirm Phone сервер может сразу вернуть сессию; интерфейс это поддерживает, но для рабочей системы используйте подтверждение владения номером.

Официальные инструкции:
- https://supabase.com/docs/guides/auth/passwords
- https://supabase.com/docs/guides/auth/phone-login

## Ограничение попыток

В Authentication → Rate Limits проверьте и задайте серверные лимиты для `/token`, `/verify`, запросов OTP и количества SMS проекта. Лимиты токена учитывают вход и обновление сессий; общий офисный IP может обслуживать много сотрудников, поэтому настройку проверяйте на ожидаемой нагрузке. В SMS-провайдере включите бюджет/лимит отправки и уведомления о расходах.

В интерфейсе: не больше 5 попыток входа или проверки кода в минуту; новая SMS — не чаще одного раза в 60 секунд. Это защита от случайных повторов, её можно обойти очисткой браузера. Защиту от подбора обеспечивает Supabase на сервере; ответ HTTP 429 корректно отображается. Настройки сервера не применялись автоматически.

https://supabase.com/docs/guides/auth/rate-limits

## Переход существующих пользователей

Войдите через Email → профиль → «Привязать телефон». Подтвердите SMS. Используется `updateUser` и `verifyOtp(type=phone_change)`, ID пользователя остаётся прежним. Роль администратора/сотрудника, блокировки и брони привязаны к ID, а не к наличию email.

Не регистрируйте отдельный телефонный аккаунт вместо привязки: новый аккаунт получает новый ID и роль сотрудника; автоматического объединения аккаунтов нет. Для пользователей, ранее входивших только через Google, сначала задайте пароль через восстановление по подтверждённому email, затем привяжите телефон. После проверки резервного доступа отключите Google Provider в Supabase; удаление кнопки из сайта само по себе не отключает провайдера на сервере. Существующие Auth-пользователи не удаляются.

Ранее не допущенные аккаунты не получают доступ от одной миграции. Предварительно разрешённый email должен быть подтверждён владельцем: другой телефон не позволяет забрать чужую зарезервированную роль. У новых телефонных регистраций роль всегда employee; metadata не может назначить admin. Управление зарегистрированным сотрудником выполняется по ID.

## Восстановление

«Забыли пароль?» → номер → SMS → новый пароль → повторный вход. Запрос OTP использует `create_user:false`, поэтому восстановление не регистрирует новые аккаунты. До успешной проверки SMS форма нового пароля не открывается. Проверка доступа к Roomly сохраняется и при восстановлении: отключённый пользователь не получает доступ к приложению.

После потери доступа к SIM обратитесь к администратору; автоматически обходить проверку владения номером нельзя. Для смены номера используйте профиль, находясь в существующем аккаунте.

## Проверки и ограничения

`npm run build` пересобирает bundle; `npm run check` проверяет синтаксис; `npm test` запускает unit/HTTP тесты. Для SQL/DOM проверок: `npm ci --prefix tests/integration`, затем `npm run test:integration`.

Новые тесты: нормализация +996, регистрация с SMS и без обязательного подтверждения, парольный вход, выход, ошибки/лимиты, восстановление, привязка телефона, запрет анонимам и отключённым, сохранение администратора и истории, повторное применение миграции, невозможность повышения роли через metadata.

Проверки выполнены локально с моделированием ответов Auth и в PostgreSQL/PGlite. Настоящая доставка SMS, настройки вашего Supabase и работа на реальном телефоне требуют приёмки владельцем после подключения провайдера. Не заявляется, что SMS уже подключены или рабочая база обновлена.
