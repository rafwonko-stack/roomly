# Roomly 1.6: вход по Email и создание сотрудников

## Что исправлено

Вход, обновление сессии и запросы данных используют корень проекта Supabase. Если в вашем config.js указан `https://nvksdnwmaippzmjqxkiv.supabase.co/rest/v1`, код удалит лишний суффикс перед построением URL. Правильный запрос входа:

`https://nvksdnwmaippzmjqxkiv.supabase.co/auth/v1/token?grant_type=password`

config.js и ключ проекта не заменяются. В проекте оставлен вход по Email/паролю; публичная регистрация, SMS, Google и восстановление пароля отсутствуют. Смена своего пароля внутри профиля сохранена. Существующие SQL, RLS, аккаунты и бронирования не изменены.

## Один раз подключите создание аккаунтов

Кнопка «Сотрудники → Создать аккаунт» требует серверной функции. Загрузка файлов на GitHub сама по себе не разворачивает функцию Supabase.

1. В Supabase откройте именно ваш проект `nvksdnwmaippzmjqxkiv` → Edge Functions → создание функции через редактор.
2. Назовите функцию **create-employee**. Добавьте два файла из `supabase/functions/create-employee/`: `index.ts` и `handler.mjs`, сохранив имена. Вставьте их содержимое в редактор и разверните функцию.
3. Для совместимости с новыми ключами подписи отключите для этой функции проверку JWT на шлюзе («Verify JWT»). Это не открывает создание аккаунтов: функция самостоятельно проверяет токен через Auth `/user`, затем текущую роль и доступ через `app_snapshot` перед каждой операцией создания. Без этих проверок никакие данные не изменяются.
4. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` используются из серверного окружения Supabase Edge Functions. Не вставляйте service_role в config.js, GitHub или браузер. Для текущего GitHub Pages дополнительная переменная не нужна. Если адрес сайта изменится, задайте серверную переменную `ROOMLY_ORIGIN` равной origin сайта (без пути и завершающего слеша).
5. В Authentication оставьте Email/password включённым, публичную регистрацию выключите (Allow new users to sign up). Google и Phone отключите, если они ещё включены. Административное создание пользователей работает отдельно от публичной регистрации.

Альтернатива через установленную Supabase CLI, из папки проекта:

```powershell
supabase login
supabase functions deploy create-employee --project-ref nvksdnwmaippzmjqxkiv --no-verify-jwt
```

SQL выполнять не требуется. Функция использует существующие `app_snapshot`, `save_member` и таблицу `members`, работает с исходной Email-схемой и с ранее подготовленной миграцией привязки к UID. Не запускайте старые миграции повторно ради этого обновления.

## Обновление сайта

Распакуйте архив обновления. Загрузите **содержимое**, а не внешнюю папку архива, в корень существующего репозитория roomly с заменой одноимённых файлов. index.html должен остаться в корне рядом с config.js и assets. Ваш существующий config.js сохраните: в архиве обновления его нет.

Дождитесь успешного GitHub Pages deployment в Actions, затем откройте https://rafwonko-stack.github.io/roomly/ и обновите Ctrl+F5. Версия подключения app.bundle.js изменена на 1.6-admin-email.

## Как создавать сотрудников

Войдите под действующим администратором → Сотрудники → Создать аккаунт. Укажите ФИО, Email, пароль 12–128 символов. После успешного создания аккаунт появится в Supabase Authentication → Users и в списке сотрудников, с ролью employee. Администратор подтверждает Email при создании; автоматическое письмо не отправляется. Передайте данные сотруднику лично. Пароль не возвращается сервером и не сохраняется в members/аудите. Сотрудник может сменить его в своём профиле.

Повторное создание того же Email не меняет существующий пароль. Email с заранее настроенной ролью admin или отключённым доступом отклоняется. Назначение роли admin остаётся отдельным явным действием в управлении правами.

При создании новый аккаунт временно блокируется в Auth. Затем сохраняется роль employee и снимается временная блокировка. Если операция оборвалась, интерфейс показывает предупреждение: проверьте Authentication → Users и members перед повтором. Если пользователь создан, но остался заблокирован, убедитесь, что роль employee и доступ верны, затем снимите блокировку Auth в Supabase. Не удаляйте существующие аккаунты и не меняйте их UUID. При потере пароля сотрудник обращается к администратору; публичного восстановления на сайте нет.

## Проверки перед передачей сотрудникам

Локально прошли тесты адаптера Auth, отсутствия публичной регистрации/восстановления, формы создания, отказа сотрудникам и неавторизованным запросам, дубликатов, блокировок, сохранения ролей и бронирований. Серверные HTTP-ответы в тестах замоканы; SQL проверяется в локальном PostgreSQL/PGlite. Реальный вход и создание пользователя в вашем Supabase не выполнялись.

После развёртывания создайте один тестовый аккаунт, проверьте его наличие в Authentication → Users, войдите под ним, выйдите и войдите повторно. Убедитесь, что у сотрудника нет раздела администрирования, а администратор сохранил права. Если вход снова не работает, в Network проверьте URL запроса: он должен содержать `/auth/v1/token`, а не `/rest/v1/auth/v1/token`.

Основание серверной реализации: [Supabase Admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [Auth API: административные операции и ban_duration](https://github.com/supabase/auth#endpoints).
