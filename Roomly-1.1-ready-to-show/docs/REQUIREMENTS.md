# Соответствие ТЗ и решения по противоречиям

Приоритет: ответы заказчика уточняют исходное ТЗ версии 1.0. Реализован согласованный MVP. Название Roomly — рабочее; бренд компании не предоставлен.

| Требование | Реализация |
|---|---|
| Веб-приложение на русском | HTML/CSS/JavaScript, без установки на ПК |
| 5 этажей, по 2 зала | 10 стартовых записей; администратор может добавлять другие залы на этих этажах |
| Вход по почте без AD | Email/пароль Supabase Auth; подтверждение email; allowlist сотрудников |
| Несколько администраторов | Роль в серверной таблице members, управление из интерфейса |
| ФИО и email обязательны | Проверка в форме и БД; email из аккаунта |
| Телефон необязателен | 7–15 цифр с допустимыми знаками форматирования |
| Все видят полные контакты | Только вошедшие и допущенные сотрудники, не анонимные посетители |
| Выбор этаж → зал → дата → время | Зависимые списки формы + быстрый выбор в расписании |
| Доступность и список/календарь | День, неделя, список; этаж/зал/дата; отдельные «Мои бронирования» |
| Двойная бронь запрещена | Серверный GiST exclusion constraint на полуоткрытом диапазоне |
| Бронь встык | Разрешена с точным совпадением конца первой и начала второй |
| Прошедшее время | Создание и перенос в прошлое запрещены на сервере |
| 08:00–20:00; шаг 30 минут | Формы и ограничения БД |
| Длительность до 8 часов | Ограничение БД и клиента |
| Горизонт 30 дней | Сегодня плюс 30 календарных дат; проверяется по времени офиса |
| Количество участников | Обязательно, не превышает вместимость |
| Изменение/отмена своей брони до начала | Право проверяется сервером, не только кнопками |
| Администратор управляет всеми бронями | Отмена активных и редактирование с соблюдением правил времени/вместимости |
| Статус, описание, оборудование зала | Формы администратора; физического удаления нет |
| Отключение и будущие брони | Список затронутых встреч и выбор сохранить/отменить; отмена атомарна |
| Уникальные идентификаторы | UUID для залов, броней, записей аудита |
| Журнал | Серверные успехи и ошибки бизнес-операций; инициатор, объект, время, результат |
| Хранение 1 год | Фильтрация истории и ежедневный SQL cron; его надо включить при установке |
| Обратная связь | Валидация, подсветка доступности, подтверждение с деталями, сообщения ошибок |
| Защита изменений | Подтверждённая учётная запись, серверные права, запрет прямых операций с таблицами |
| Компактность | Нет растровых медиа, стороннего JS в клиенте, node_modules в поставке |
| Анимации и визуализация | SVG-планы залов, состояния карточек, мягкое появление, анимация иллюстрации; reduced-motion |

## Явные допущения

1. **15 минут против шага 30.** При сохранении получасовой сетки минимальная фактическая встреча — 30 минут. Ограничение БД допускает длительность от 15, но границы интервала кратны 30, поэтому 15-минутную бронь создать нельзя. При подтверждении необходимости 15 минут нужно одновременно изменить сетку и ограничения БД.
2. **Часовой пояс не назван.** Начальная настройка `Asia/Bishkek`; её требуется подтвердить или заменить до наполнения рабочих данных. Часовой пояс компьютера пользователя не влияет на расчёты.
3. **Рабочие дни не определены.** Бронирование разрешено каждый день с 08:00 до 20:00, включая выходные. Календарь праздников не придуман.
4. **Залы не описаны поимённо.** Названия, оборудование и 24/8 мест — редактируемые стартовые значения.
5. **Авторизация через почту.** Выбран email + пароль с подтверждением почты и восстановлением доступа. Беспарольная OTP-авторизация и AD не входят в эту реализацию.
6. **Тема встречи.** Добавлено короткое обязательное название до 100 символов для понятного расписания. Если его не нужно раскрывать коллегам, используйте нейтральные названия.
7. **Неактивный зал.** Новые и переносимые в него брони запрещены. Сохранённые при отключении существующие брони видны в списках/неделе и могут быть отменены или перенесены в активный зал.
8. **Изменения прошлых встреч.** Администратор может отменить активную запись независимо от начала. Перенос на прошедшее время запрещён всем; для исправления исторических данных нужен отдельный регламент владельца БД.
9. **Деактивация сотрудника.** Блокирует последующие обращения к API. Его существующие бронирования сохраняются, чтобы администратор принял решение отдельно.
10. **История.** Брони сохраняются 365 дней по дате встречи, журнал — 1 календарный год по времени операции. Физическая очистка ежедневная, поэтому технически возможен остаток менее суток; API скрывает более старые записи сразу.

## Второй этап — сознательно не включён

- AD/SSO и перенос в закрытую корпоративную сеть.
- Повторяющиеся встречи и освобождение при неявке.
- Outlook/Google Calendar и уведомления о встречах на почту.
- Отчёты загрузки, экспорт Excel, резервное копирование с проверкой восстановления.
- Формальная приёмка мобильных устройств, расширенные SLA и эксплуатационный мониторинг.

Интерфейс адаптируется к узкой ширине уже сейчас, но отдельная мобильная приёмка по ответам заказчика относится ко второму этапу. Поддержка актуальных Chrome, Edge, Firefox и Safari заложена стандартными браузерными API; проверка всех этих браузеров в данном окружении не выполнена.

## Ответственность при запуске

Заказчик подтверждает фактические залы, вместимость, часовой пояс, список сотрудников и администраторов. Охрана здания принимает пользовательские сценарии. Отдел разработки контролирует хостинг, SMTP, квоты, обновления и переход ко второму этапу.
